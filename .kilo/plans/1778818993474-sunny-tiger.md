# Plan: Implement and Clean Up `src/procureos_mcp/tools/`

## Goal
Create a detailed implementation plan for the `tools/` folder based on `Plans/FOLDER_STRUCTURE_PLAN.md`, while checking function signatures across the current codebase for discrepancies.

The `tools/` folder should be the MCP-facing bridge layer:

- Receive structured input from Claude Desktop through MCP tools.
- Call reusable functions from `src/procureos_mcp/db/schema.py` and `src/procureos_mcp/db/queries.py`.
- Return JSON/text responses using `src/procureos_mcp/utils/json_helpers.py`.
- Avoid direct database connection handling, SQL execution, configuration loading, or server startup.

## Files In Scope

Primary files:

- `src/procureos_mcp/tools/__init__.py`
- `src/procureos_mcp/tools/database_tools.py`

Related files to verify while implementing:

- `src/procureos_mcp/server.py`
- `src/procureos_mcp/db/schema.py`
- `src/procureos_mcp/db/queries.py`
- `src/procureos_mcp/utils/json_helpers.py`
- `schemas.py`
- `requirements.txt`

## Current Findings

### Folder Plan Expectations

`Plans/FOLDER_STRUCTURE_PLAN.md` says:

- `tools/` contains MCP tool definitions exposed to Claude Desktop.
- `tools/database_tools.py` registers database-related MCP tools.
- `tools/database_tools.py` should import from `db/schema.py` and `db/queries.py`.
- The tool layer should not manage connection configuration.
- Import direction should be:

```text
server.py
    imports tools

tools/database_tools.py
    imports db/schema.py
    imports db/queries.py

db/schema.py and db/queries.py
    import db/connection.py
    import utils/json_helpers.py
```

### Current `tools/database_tools.py`

Current registered tools:

- `search_supplier_catalog(query: SourcingQuery) -> str`
- `draft_purchase_order(query: DraftPOQuery) -> str`
- `check_po_status(query: OrderStatusQuery) -> str`

Current local input models:

- `SourcingQuery`
- `PurchaseItem`
- `DraftPOQuery`
- `OrderStatusQuery`

Current query dependencies:

Current utility dependency:

- `to_json(data) -> str`

Current schema dependency:

- `import schemas` from root-level `schemas.py`

## Signature And Import Discrepancies Found

### 1. Folder plan example vs current query signatures

The plan example shows:

```python
def search_vendor_products(search_text: str) -> str:
    return search_products(search_text)
```

Current implementation has:

```python
def search_products(query_terms: str, max_unit_price: Optional[float], limit: int = 10)
```

Plan impact:

- Do not call `search_products(search_text)` unless `max_unit_price` is given a default in `db/queries.py` or the tools layer passes `None`.
- Current `SourcingQuery` maps correctly to the current signature by passing `query_terms` and `max_unit_price`.
- If adding a simple text search MCP tool, it must call `search_products(query_terms=search_text, max_unit_price=None)`.

### 2. `tools/database_tools.py` imports root-level `schemas`

Current code:

```python
import schemas
```

Issue:

- This works only if the project root is on `PYTHONPATH`.
- It breaks the clean `src/procureos_mcp` package boundary described in the folder plan.
- It is inconsistent with package imports like `from procureos_mcp.db.queries import ...`.

Plan impact:

- Short-term implementation can preserve `import schemas` if not moving files yet.
- Preferred cleanup is to move or mirror `schemas.py` into the package, for example `src/procureos_mcp/schemas.py`, then update imports to `from procureos_mcp import schemas` or `from procureos_mcp.schemas import ProductSchema, ...`.
- Since this plan is specifically for `tools/`, do not move `schemas.py` unless the implementation scope is expanded.

### 3. `server.py` currently contains merge-conflict markers

Current `server.py` includes:

```text
<<<<<<< HEAD
=======
>>>>>>> 68bace88063ba09fb3c3c2596cacc646ce5d4c04
```

Issue:

- This will cause Python syntax errors and prevent tool registration from being loaded.

Plan impact:

- Although not inside `tools/`, implementation should include a prerequisite cleanup step to remove these markers if code execution or validation is requested.
- Keep the final server content minimal and consistent with the folder plan.

### 4. `config.py` and `connection.py` differ from the earlier package-init plan

Current `connection.py`:

```python
from procureos_mcp.config import get_db_dsn

def get_connection():
    return psycopg2.connect(get_db_dsn())
```

Current `config.py` provides `get_db_dsn()`, not only `DB_CONFIG`.

Plan impact:

- This does not directly break the tools folder.
- Do not change this as part of tools implementation unless the user requests config cleanup.

### 5. Tool input model field types vs schema/query functions

Current `PurchaseItem.product_id` is `uuid.UUID`.

Current `get_product_by_id(product_id: str)` expects `str`.

Current code correctly calls:

```python
get_product_by_id(str(item.product_id))
```

Current `DraftPOQuery.buyer_email` is `EmailStr`.

Current `get_user_by_email(email: str)` expects `str`.

Pydantic `EmailStr` behaves like a string in practice, but for strict consistency the tool can call:

```python
get_user_by_email(str(query.buyer_email))
```

### 6. Order total type mismatch risk

Current `OrderSchema.total` expects `Decimal`.

Current tool computes:

```python
total_amount = 0.0
unit_price = float(prod.price)
total_amount += unit_price * item.quantity
```

Issue:

- This converts database/product decimal pricing to float, then validates into `Decimal`.
- It can introduce precision issues for money.

Plan impact:

- Prefer `Decimal("0.00")` and avoid float conversion in `draft_purchase_order`.
- Use `prod.price * item.quantity` if `prod.price` is a `Decimal`.

### 7. `register_database_tools` return annotation missing

Current:

```python
def register_database_tools(mcp):
```

Earlier plan expected:

```python
def register_database_tools(mcp) -> None:
```

Plan impact:

- Add `-> None` for consistency.
- Keep `mcp` untyped unless a stable FastMCP type import is desired. Avoid importing FastMCP in tools only for typing unless using `TYPE_CHECKING`, because the folder plan wants tools to know MCP only at registration points.

### 8. `tools/__init__.py` is empty

This is acceptable.

Plan impact:

- Optionally export `register_database_tools` for cleaner imports:

```python
from procureos_mcp.tools.database_tools import register_database_tools

__all__ = ["register_database_tools"]
```

- If implemented, `server.py` could later import from `procureos_mcp.tools`, but this is optional.
- Minimal approach: leave `tools/__init__.py` empty.

## Proposed Tool Set

Implement or retain these MCP tools in `database_tools.py`:

### 1. `list_database_tables() -> str`

Purpose:

- Expose database table discovery to Claude Desktop.

Dependency:

- `list_tables()` from `procureos_mcp.db.schema`

Return shape:

```json
{
  "status": "success",
  "data": ["products", "orders"]
}
```

Error shape:

```json
{
  "status": "error",
  "error": "..."
}
```

### 2. `describe_database_table(table_name: str) -> str`

Purpose:

- Let Claude inspect columns for a specific table.

Dependency:

- `describe_table(table_name: str)` from `procureos_mcp.db.schema`

Return shape:

```json
{
  "status": "success",
  "data": [...]
}
```

### 3. `search_supplier_catalog(query: SourcingQuery) -> str`

Purpose:

- Search products by name/description and optional max unit price.

Dependency:

- `search_products(query_terms: str, max_unit_price: Optional[float], limit: int = 10)`

Signature compatibility:

- Current tool call already matches current query function.
- Optional improvement: add `limit` to `SourcingQuery` so the tool can pass it explicitly.

Recommended model:

```python
class SourcingQuery(BaseModel):
    query_terms: str = Field(..., description="Keywords to search in product name or description.")
    max_unit_price: Optional[float] = Field(default=None, description="Maximum price per unit.")
    limit: int = Field(default=10, ge=1, le=50, description="Maximum number of products to return.")
```

### 4. `draft_purchase_order(query: DraftPOQuery) -> str`

Purpose:

- Validate buyer and product IDs, calculate totals, create order, create order items, return new order details.

Dependencies:

- `get_user_by_email(email: str)`
- `get_product_by_id(product_id: str)`
- `create_order(order_row: dict)`
- `create_order_items(order_items: List[dict])`

Signature compatibility:

- Convert `EmailStr` to `str` when calling `get_user_by_email`.
- Convert `uuid.UUID` to `str` when calling `get_product_by_id`.

Money handling:

- Use `Decimal`, not `float`, for `total_amount`.

### 5. `check_po_status(query: OrderStatusQuery) -> str`

Purpose:

- Return order details by order number.

Dependency:

- `get_order_by_number(order_number: str)`

Signature compatibility:

- Current call matches current query function.

## Step-By-Step Implementation Plan

### Step 1: Fix prerequisite syntax issue in `server.py`

Remove merge-conflict markers from `src/procureos_mcp/server.py` before validating imports or compilation.

Target content should remain:

```python
"""ProcureOS MCP server entrypoint."""

from mcp.server.fastmcp import FastMCP

from procureos_mcp.tools.database_tools import register_database_tools

mcp = FastMCP("procureos-db-server")

register_database_tools(mcp)


def main() -> None:
    """Run the ProcureOS MCP server."""
    mcp.run()


if __name__ == "__main__":
    main()
```

Rationale:

- This is outside `tools/`, but required because the tools folder is loaded through `server.py`.

### Step 2: Update imports in `database_tools.py`

Add schema discovery imports:

```python
from procureos_mcp.db.schema import describe_table, list_tables
```

Keep current query imports, but ensure they match actual function names in `db/queries.py`:

```python
from procureos_mcp.db.queries import (
    create_order,
    create_order_items,
    get_order_by_number,
    get_product_by_id,
    get_user_by_email,
    search_products,
)
```

Keep JSON helper import:

```python
from procureos_mcp.utils.json_helpers import to_json
```

Handle schemas import in the least disruptive way:

```python
import schemas
```

Preferred future cleanup:

- Move `schemas.py` into `src/procureos_mcp/schemas.py` and update this import.
- Do not include that move in this tools-only implementation unless explicitly approved.

### Step 3: Add `register_database_tools(mcp) -> None`

Change the registration signature from:

```python
def register_database_tools(mcp):
```

to:

```python
def register_database_tools(mcp) -> None:
```

Do not return anything from this function.

### Step 4: Add schema inspection MCP tools first

Inside `register_database_tools`, add:

```python
@mcp.tool()
def list_database_tables() -> str:
    """List public database tables."""
    try:
        return to_json({"status": "success", "data": list_tables()})
    except Exception as exc:
        return to_json({"status": "error", "error": str(exc)})
```

Then add:

```python
@mcp.tool()
def describe_database_table(table_name: str) -> str:
    """Describe columns for a public database table."""
    try:
        return to_json({"status": "success", "data": describe_table(table_name)})
    except Exception as exc:
        return to_json({"status": "error", "error": str(exc)})
```

Rationale:

- These are explicitly recommended in `Plans/FOLDER_STRUCTURE_PLAN.md`.
- They help Claude inspect schema before querying products/orders.

### Step 5: Refine `SourcingQuery`

Current fields:

- `query_terms: str`
- `max_unit_price: Optional[float]`

Recommended addition:

- `limit: int = Field(default=10, ge=1, le=50, description="Maximum number of products to return.")`

Then update `search_supplier_catalog` call:

```python
raw_results = search_products(
    query_terms=query.query_terms,
    max_unit_price=query.max_unit_price,
    limit=query.limit,
)
```

Rationale:

- This fully matches the current `search_products` signature.
- Keeps result size controlled for Claude Desktop.

### Step 6: Make `draft_purchase_order` type-safe for current query signatures

Update buyer lookup:

```python
user_row = get_user_by_email(str(query.buyer_email))
```

Keep product lookup conversion:

```python
prod_row = get_product_by_id(str(item.product_id))
```

Replace float money calculation:

```python
from decimal import Decimal

total_amount = Decimal("0.00")
...
total_amount += prod.price * item.quantity
```

Rationale:

- Aligns `EmailStr` with `get_user_by_email(email: str)`.
- Aligns `UUID` with `get_product_by_id(product_id: str)`.
- Avoids float precision issues for purchase totals.

### Step 7: Standardize response envelopes

Use consistent response keys across all tools:




Existing responses can be kept if minimizing changes, but standardizing them will make Claude responses more predictable.

## Risks And Follow-Up Items

### Root-level `schemas.py`

Risk:

- `import schemas` can fail depending on working directory and `PYTHONPATH`.

Recommended follow-up:

- Move `schemas.py` into `src/procureos_mcp/schemas.py`.
- Update imports in `database_tools.py`, `pipeline.py`, and tests.

### Missing dependency for `EmailStr`

Pydantic `EmailStr` usually requires `email-validator`.

Risk:

- Importing `DraftPOQuery` may fail if `email-validator` is not installed.

Recommended follow-up:

- Add `email-validator` to `requirements.txt` or use plain `str` with validation handled elsewhere.

### Database write transaction behavior

`create_order()` and `create_order_items()` each open their own connection context.

Risk:

- Order creation can succeed while item creation fails, leaving partial state.

Recommended follow-up:

- Move purchase order creation into a single db-layer transaction function, then let the tool call only that function.

### Tool layer currently contains business orchestration

The folder plan prefers tools to bridge MCP to db functions.

Risk:

- `draft_purchase_order` contains significant business logic in the tools layer.

Recommended follow-up:

- Move order drafting orchestration to `db/queries.py` or a future service layer if the project grows.

## Final Expected State After Implementation

- `database_tools.py` registers schema inspection tools and procurement tools.
- All tool calls match current function signatures in `db/schema.py` and `db/queries.py`.
- `register_database_tools` has a clear `-> None` annotation.
- `server.py` can import `register_database_tools` without syntax errors.
- The tools layer does not directly import connection/config modules or execute SQL.
- JSON responses are generated via `to_json()`.
